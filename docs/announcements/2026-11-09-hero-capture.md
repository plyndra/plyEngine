# Hero capture — provenance

`hero-capture.gif` (960 px, 12 fps, 191 frames, ~16 s) and `hero-capture.mp4`
(1280x720) are **scripted captures**, regenerated by
`scripts/capture-hero.sh`.

## What the frames are

`ply_companion --verify` plays the reference platformer with the demo's
Autopilot. The autopilot does not touch game state directly: it synthesises
`ply::companion::ControllerState` values and pushes them into the
`CompanionInput` queue per slot, which is the same path a phone's WebSocket
frame takes (`examples/companion/main.cpp`, the `if (verify)` block). The four
players therefore move through the real slot routing, not through a scripted
animation.

The HUD on frame 1 says so on screen: `scripted capture: 4 slots via the phone
input path`. It is not a recording of four physical phones.

## Why it is reproducible

The demo advances on a fixed timestep and the autopilot is deterministic, so
the same build and stride produce the same frame sequence. The run also asserts
outcomes (`verify: PASS`): coins collected, deaths to pit and saw, all four
slots moving independently, P1 reaching the flag.

## Regenerating

```sh
cmake --build build --target ply_companion -j
scripts/capture-hero.sh                      # writes docs/announcements/hero-capture.{gif,mp4}
```

Requires `xvfb-run`, `ffmpeg`, Mesa software GL, and `companion/dist` (built
with `cd companion && npm ci && npm run build`).

## Publishing rules

- Keep the `scripted capture` HUD line visible, or state it in the surrounding
  text. Never present these frames as four physical phones.
- GIF budget: ≤8 MB, 960 px (current: ~0.4 MB). A heavier cut means fewer
  colours or a shorter range, not a bigger download on the landing page.
- The MP4 is the full-resolution copy for channels that penalise GIFs.
